# Підключення бази даних

Форми заявок пишуть у Postgres. Поки змінні середовища не задані, форми на сайті
заблоковані й прямо повідомляють, що приймання заявок не налаштоване — вони не
показують «заявку надіслано», якщо вона нікуди не йде.

## Чому Supabase

Потрібна була база, у яку може писати статичний сайт без власного сервера.
Варіанти, які розглядалися:

| Рішення | Плюси | Мінуси | Вартість |
|---|---|---|---|
| **Supabase** | Це звичайний Postgres із HTTP-доступом. Є політики рядкового доступу, панель для перегляду заявок, експорт у CSV | Треба акуратно налаштувати політики, бо ключ публічний | Безкоштовно до 500 МБ |
| Netlify Forms | Нічого не треба налаштовувати взагалі | Це не база даних: немає схеми, звʼязків і запитів. Тупикова гілка | Безкоштовно до 100 заявок на місяць |
| Власний ASP.NET Core API + Postgres | Повний контроль, свій код | Потрібен окремий хостинг і час на розгортання | від 5 $/міс |

Вибрано Supabase з однієї конкретної причини: **це не окрема платформа зі своїм
форматом даних, а керований Postgres**. Supabase дає звичайний рядок підключення
(`Project Settings → Database → Connection string`). Коли бекенд на ASP.NET Core
буде готовий, EF Core підключається до тієї самої бази тим самим рядком —
нічого мігрувати не доведеться. Фронтенд просто перестане ходити в базу напряму
і почне звертатися до вашого API.

## Налаштування, 10 хвилин

1. **Створити проєкт.** [supabase.com](https://supabase.com) → New project.
   Регіон беріть європейський (Frankfurt), бо дані стосуються людей з України та ЄС.
   Пароль до бази збережіть у менеджері паролів — він знадобиться для EF Core.

2. **Створити таблиці.** SQL Editor → New query → вставити весь вміст `db/schema.sql` → Run.
   Скрипт можна запускати повторно, він не ламає наявні дані.

3. **Перевірити політики.** У тому ж SQL Editor виконати:
   ```sql
   select tablename, policyname, cmd, roles from pg_policies where schemaname='public';
   ```
   Має бути рівно два рядки, обидва з `cmd = INSERT` і `roles = {anon}`.
   Якщо зʼявився рядок із `SELECT` — зупиніться: це означає, що будь-хто зможе
   прочитати всі заявки.

4. **Взяти ключі.** Project Settings → API:
   - `Project URL` → у змінну `PUBLIC_SUPABASE_URL`
   - `anon public` ключ → у змінну `PUBLIC_SUPABASE_ANON_KEY`

   Ключ `service_role` не чіпайте. Він обходить усі політики доступу
   й у фронтенді не має опинитися за жодних обставин.

5. **Прописати в Netlify.** Site configuration → Environment variables → додати обидві
   змінні. Потім Deploys → Trigger deploy → Clear cache and deploy site.

6. **Перевірити.** Відкрити сайт, подати тестову заявку.
   У Supabase: Table Editor → `applications` → має зʼявитися рядок.

## Чому публічний ключ у коді — це не дірка

`anon` ключ видно в коді будь-якої сторінки, і це задумано саме так. Він лише
повідомляє базі, що запит анонімний. Що з цим анонімом дозволено робити,
вирішують політики: у нас для нього є **тільки** дозвіл на `INSERT`.
Політик на `SELECT`, `UPDATE` і `DELETE` не створено взагалі, тому прочитати
чи змінити заявки з цим ключем неможливо.

Перевірити самостійно:

```bash
curl "$PUBLIC_SUPABASE_URL/rest/v1/applications?select=*" \
  -H "apikey: $PUBLIC_SUPABASE_ANON_KEY"
```

Має повернутися порожній масив `[]`, а не список заявок.

## Що лишається зробити до реального запуску

- Заповнити реквізити володільця даних у політиці конфіденційності
- Дати політику на перевірку юристу
- Налаштувати сповіщення про нові заявки (Supabase → Database Webhooks)
- Продумати, хто з команди має доступ до панелі й під якими акаунтами
- Додати захист від спаму, якщо пастки для ботів виявиться замало
  (у формах уже є приховане поле-пастка)

## Обмеження поточної версії

- Файли резюме не зберігаються, тільки посилання. Це свідоме рішення, див. коментар у `db/schema.sql`
- Немає особистого кабінету: статус заявки людина дізнається листом, а не на сайті
- Видалення даних на вимогу виконується вручну через панель
- Немає автоматичного листа-підтвердження учаснику. Поки це ручна робота
